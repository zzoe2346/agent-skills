# 이력서와 포트폴리오 검토

채용 담당자가 빠르게 이해하고 면접에서 확인할 수 있도록 기여와 성과를 정확하게 표현한다. 사용자 지정 문체와 이력서 구성을 존중하고 의미 있는 개선에 집중한다.

## 검토 범위와 근거

- 최신 이력서를 사용한다. 이전 제안의 누락 점검 요청이면 최신본과 실제 제안을 비교하고, 사용자가 의도적으로 생략한 내용은 다시 넣도록 강제하지 않는다.
- PDF는 추출 텍스트와 렌더링을 함께 확인한다. 텍스트 추출 과정의 띄어쓰기 오류를 실제 문서의 오탈자로 보고하지 않는다. PDF의 실제 링크 주석을 확인하고, 보이는 링크 표시만으로 연결됐다고 판단하지 않는다.
- 제공된 경험 기록과 연결된 포트폴리오를 읽어 주장과 기여 범위를 대조한다. 사용자의 최신 설명과 직접 수정 사항을 반영한다. 확인하지 않은 문서는 확인했다고 말하지 않는다.
- 지원 회사에 맞춰 바꾸는 Introduce는 그 의도를 존중한다. 회사별 소개를 공통 소개로 교체하도록 강제하지 않는다.

## 판단 기준

1. 기여: 직접 발견, 제안, 설계, 구현, 배포한 일과 검토 참여를 구분한다. 다른 사람이 설계하고 구현했다면 그 설계의 검토에 참여했다고 표현한다. 설명할 수 있다는 사실만으로 본인 수행이 되지는 않는다.
2. 명확성: 구체적인 문제, 행동, 결과가 이어지는지 확인한다. 재사용 기준, 조회 대상, 상태 범위 등 문장의 의미를 바꾸는 기준을 명시한다. 기술명만 나열하거나 제목과 본문을 반복하지 않는다.
3. 성과: 운영 전후 관찰, 통제된 테스트, 타 팀 집계 등을 구분한다. 측정 대상, 데이터 규모, 평균과 p99, 집계 기간, 출처를 필요한 만큼 남긴다. 여러 변화가 섞인 관찰을 단일 변경의 확정적인 인과로 과장하지 않는다.
4. 일관성: 이력서, 포트폴리오, 실제 자료의 용어, 수치, 담당 역할, 완료 여부가 맞는지 확인한다. 설계 검토, 구현 완료, 운영 적용을 구분한다.
5. 표현: 전문용어는 정확성과 역량을 드러내는 데 활용한다. 가운뎃점(`·`)은 남발하지 않되 유용하면 사용한다. 짧게 만들기 위해 기술적 의미를 삭제하지 않는다.

실제 문제가 있는 항목만 우선순위를 매겨 제안한다. 확인된 오류와 선택적인 개선을 구분한다. 전체를 일괄 재작성하기보다 AS IS → TO BE와 수정 이유를 제공하고, 사용자가 요청하면 프로젝트 전체 불릿 구성도 제시한다. 새로운 어필 후보는 근거가 있는 것만 제안하고 필요한 확인 질문을 붙인다.

## 링크와 제출 점검

- 링크 표시 문구, PDF에 저장된 실제 주소, 도착한 문서 제목과 내용을 대조한다. 올바른 사이트가 열려도 다른 프로젝트 문서라면 매핑 문제다.
- 로그인 없이 접근 가능한지 검증해달라는 요청에는 기존 계정에서 로그아웃하거나 공유 설정을 바꾸지 않는다. 가능하면 별도 시크릿 창 또는 명확히 인증되지 않은 세션으로 실제 URL을 열고 본문 접근을 확인한다.
- 로그인 안내 배너와 본문 접근 차단을 구분한다. HTTP 200, 검색 결과, 연결된 계정의 MCP 조회 성공만으로 익명 접근 성공이라고 말하지 않는다. 웹 조회 도구의 404도 비공개라는 확정 증거가 아니다.
- 실제 확인한 범위를 보고한다. 본문 접근만 검증했다면 모든 이미지와 다이어그램 렌더링까지 검증했다고 하지 않는다. 검증 도구가 없으면 그 한계를 명시한다.
- 확인용으로 만든 창이나 탭만 정리하고 사용자 기존 창은 유지한다. 이력서 검토는 공개 게시나 권한 변경의 승인이 아니다.

다양한 시각의 서브에이전트 검토는 사용자가 요청했거나 별도로 허용된 경우에 활용한다. 문구를 조금 고칠 때마다 전체 검토를 반복하지 않는다.

## 전달

가장 중요한 발견과 수정안을 먼저 제시한다. 제출 가능 여부는 실제 검토 결과와 남은 확인 사항에 맞춰 설명한다. 내용 검토, 링크 매핑, 익명 접근, 레이아웃 중 확인한 항목을 구분해 사용자가 다음 행동을 알 수 있게 한다. 검토 요청만으로 원본이나 외부 문서를 자동 수정하지 않는다.
