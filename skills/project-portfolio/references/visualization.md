# 포트폴리오 시각화 기준

시각화는 채용 담당자가 본문에서 이해하기 어려운 관계나 동작을 더 빠르게 파악하게 할 때만 추가한다. 장식용 삽화와 동일한 설명의 중복은 피한다.

| 설명하려는 내용 | 우선 검토할 형식 |
| --- | --- |
| 단일 테이블에서 저장되는 실제 레코드 | 표 |
| 데이터 관계와 관리 단위 | Mermaid ERD |
| 호출 순서, 경합, 실패 처리 | Mermaid sequenceDiagram |
| 상태와 분기 | Mermaid stateDiagram 또는 flowchart |
| 내부와 외부 시스템, 여러 API의 연결 | Mermaid flowchart 또는 편집 가능한 draw.io |
| 성능 전후 차이 | 간단한 표, 비교 대상이 많으면 차트 |

- 밝은 배경에 흑백과 파랑 강조를 기본 후보로 삼되 사용자가 고른 스타일을 우선한다. 과도한 설명을 이미지에 넣지 않는다.
- 실제로 확인한 엔티티와 배포 단위를 표현한다. 그림을 완성하기 위해 박스 테이블, DB, API 또는 시스템을 임의로 추가하지 않는다. 설명용 개념 모델이면 실제 스키마와 구분한다.
- 아키텍처에는 내부와 외부 경계, 호출 방향, 호출 목적, 담당 기능을 표시한다. 사용자가 확정한 배포 API 이름을 문서의 프로젝트 또는 모듈 이름으로 바꾸지 않는다.
- 일부 기능만 담당했다면 전체 애플리케이션을 본인이 개발한 것처럼 색칠하지 않는다. 강조색의 의미를 구체적으로 표시한다.
- 화살표는 인증 헤더 이름만 붙이기보다 영수증 템플릿 요청, URL 단축 요청 중계 등 호출 목적을 먼저 보여준다. 추측한 데이터 이동은 사실로 표현하지 않는다.
- 사용자의 방향 요청을 반영한다. draw.io 텍스트와 연결선 라벨은 실제 렌더링에서 읽히는지 확인하고 편집 가능한 원본을 제공한다.
- Mermaid를 노션에 넣으면 코드 블록 언어와 실제 렌더링을 확인한다. SVG나 이미지의 지원 여부를 단정하지 않고 사용 가능한 방식으로 넣는다.
- 새 시각화를 기존 문서에 교체 반영하기 전에는 미리보기를 보여준다. 검증된 사실을 바꾸지 않는 한 사용자 확인이 끝난 수정은 계속 진행한다.

전용 다이어그램 스킬이 있으면 제작에 활용하고, 없으면 가능한 도구로 만든다. 특정 플러그인 설치를 이 작업의 필수 조건으로 만들지 않는다.
