# JD 맞춤 Introduce 작성

핵심은 어떤 경험으로 이 조직의 어떤 문제 해결에 기여할 수 있는지를 보여주는 것이다. JD의 표현을 반복하거나 기술 스택을 단순 나열하지 않는다.

## 공고와 경험 연결

- 사용자가 제공한 JD와 최신 이력서를 우선 사용한다. 공고가 그대로 제공됐으면 불필요하게 회사 전반을 조사하지 않는다. 공고 URL만 주어졌거나 최신 정보 확인을 요청했으면 해당 원문을 확인한다.
- 조직의 실제 과제, 주요 업무, 필수 역량, 우대 역량을 구분한다. 모든 항목을 소개에 담으려 하지 않고 지원자를 잘 설명하는 연결점을 선택한다.
- 경험의 구체적인 근거와 연결할 기여를 작업 중 정리한다. 직접 경험, 유사한 원리의 경험, 입사 후 확장할 영역을 구분한다.
- 다른 도메인의 모델 개선 경험은 요구사항과 관계를 구조화하는 역량으로 연결할 수 있다. 회사 내부 스키마나 실제 설계 문제를 아는 것처럼 쓰지는 않는다.
- SSO 연동 경험만으로 OAuth2/OIDC 인증 서버 설계 경험을 주장하거나, 관계형 모델링 경험을 GraphDB 경험으로 바꾸지 않는다. AI 활용, 테스트 코드 작성, AWS 구성 경험도 확인된 범위만 사용한다. Mock Agent로 연동을 검증한 경험을 자동화 테스트 작성으로 확대하지 않는다.
- 연차 요건을 맞추기 위해 경력 기간을 늘리거나 검토 참여를 설계 주도 경험으로 바꾸지 않는다. 해당 경험이 왜 유용한지 설명한다.

## 문구 구성

사용자 지정 길이와 형식을 우선한다. 형식이 열려 있으면 간결한 문단형 또는 짧은 정체성 문장과 2~3개 불릿을 검토한다. 기존 소개에 얽매이지 말라는 요청이면 기존 구조를 유지하지 않아도 된다.

- 경험 → 그 경험에서 드러난 역량 → JD의 과제에 대한 기여를 연결한다. 각 불릿에서 연결하거나 마지막 문장에 묶을 수 있다.
- 과거 경험은 실제 행동으로 쓰고, 향후 기여는 의지 또는 가능한 역량으로 표현한다. 입사 후 성과를 보장하는 문장은 피한다.
- 인증, 데이터 모델, 서비스 설계와 운영 등 서로 다른 강점을 선택해 중복을 줄인다. 오너십과 협업은 구체적인 계약 조율, 요구사항 확정, 검증 지원, 운영 반영 사례로 보여준다.
- 모든 경험과 수치를 소개에 다시 적지 않는다. 이력서 불릿과 연결 문서가 설명할 상세 판단은 필요한 만큼만 남긴다.
- 전문용어는 공고와 실제 경험을 정확히 연결할 때 활용한다. 가운뎃점(`·`)은 남발하지 않되 유용하면 사용한다. 회사를 칭찬하는 일반 문구보다 경험과 기여를 우선한다.

## 여러 안 제시

사용자가 요청한 개수에 맞춘다. 단순한 동의어 교체 대신 인증 중심, 균형형, 협업과 검증, 설계부터 운영, AI 활용처럼 실제 강점과 구성의 차이를 만든다. 모든 버전에 모든 우대사항을 넣을 필요는 없다.

완성 문구를 바로 복사해 쓸 수 있게 제공한다. 가장 적합한 안과 짧은 이유를 함께 제시하고, 불릿형과 문단형 중 선택할 수 있다면 각각의 추천을 구분한다. 선택과 편집은 사용자에게 맡기고 승인 없이 이력서나 외부 프로필에 반영하지 않는다.
